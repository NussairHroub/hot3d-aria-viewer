Release · provenance · method

What the release contains, and how this site was made from it

HOT3D publishes one folder per recording: a VRS recording, motion-capture ground truth for the headset, both hands and every object, 2D boxes, quality masks, and Aria's own machine-perception output. This page lists those files, gives the sizes involved, and states every step between them and the figures on the other pages, so a reader can check the numbers or rebuild the site. The derived payload is two files per recording, not one: the release licenses hand annotations more restrictively than everything else, so the hand data is kept in a file of its own.

One recording folder, file by file

A recording is identified as P00xx_<hash> — participant, then an opaque id. The release delivers each recording as a set of downloadable pieces that unpack into the layout below. Names in the last column are the pages of this site that read the file, through the derived payload rather than directly.

recording.vrs main_vrs The recording itself. Three camera streams — RGB 214-1 at 1408×1408 and the monochrome SLAM pair 1201-1, 1201-2 at 640×480, all 30 fps — alongside the other device streams Aria writes, with per-frame device timestamps. Sequence viewer (the mp4), Cameras (the SLAM stills)

dynamic_objects.csv ground_truth Motion-capture pose of every object in the recording, per timestamp, mapping that object's model frame to world. Objects, 3D scene, Sequence viewer
box2d_objects.csv ground_truth A 2D box per object per camera stream, with the visibility ratio (0–1) the release reports for it. Sequence viewer overlay, Objects
box2d_hands.csv ground_truth The same for the left and right hand. Sequence viewer overlay, Hands — through the hand payload, not the sequence one

masks/mask_*.csv ground_truth Seven per-frame quality signals, one file each — qa_pass, good_exposure, hand_visible, object_visible, hand_pose_available, headset_pose_available, object_pose_available — with a column per camera stream. mps/eye_gaze/ mps_eye_gaze Eye gaze in the Central Pupil Frame: per-eye yaw, pitch and gaze depth, as a general estimate and, where the wearer was calibrated, a personalised one. Eye gaze — the payload records which variant was taken in gaze.source

Four files per recording

The release licenses its hand annotations under CC BY-NC-SA 4.0 and everything else under CC BY-SA 4.0. One file holding both cannot be licensed lawfully: BY-SA forbids imposing the extra NonCommercial restriction on BY-SA material, and BY-NC-SA cannot be dropped from the hand data. So the derived payload for a recording is written as separate files, each carrying one licence, and a page that only needs poses, boxes, points or gaze never loads the non-commercial half.

A second split is about weight rather than licensing. Two thirds of the first payload was 2D boxes for the two monochrome SLAM cameras, which no page on this site draws — the viewer plays the RGB stream. Those boxes are published beside the payload instead of inside it, which is why the sequence file carries only boxes.rgb. The numbers are unchanged; they are one fetch further away.

Sizes

The full HOT3D release is about 920 GB: 526 GB for the 198 Aria recordings and 394 GB for the 226 Quest 3 recordings, plus a separate archive of the 33-object model library. The two halves cover the same task and the same object library on different headsets; this site only reads the Aria half.

From the release to the payload

One extraction pass per recording writes both data/seq/<SEQ>.json and data/hands/<SEQ>.hands.json; the split is the last thing the pass does, and everything below is applied the same way on both sides of it. The numbers are read from — and its hand file now, as an example. Nothing is re-estimated anywhere in this pipeline — every pose, box and mask is the released value, moved onto a common frame grid and re-encoded.

  1. The frame grid is the RGB stream. Row i of every per-frame array on this site is RGB frame i of the VRS stream 214-1, on the camera's own 30 Hz clock. This recording has — frames over — at — fps, and t holds the seconds from the first frame.
  2. Ground truth is annotated at 60 Hz and resampled onto it. The release annotates the RGB exposures interleaved with the two SLAM cameras, so the annotation grid runs at twice the frame rate. Each pose, box and mask is taken from the nearest annotated timestamp, accepted only within 8 ms; beyond that the frame is left unannotated — NaN in a float array, 255 in a mask. —
  3. Hand annotations are written to a second file. The UmeTrack wrist poses, joint angles, confidences and 2D hand boxes, and the hand_visible and hand_pose_available masks, go to data/hands/<SEQ>.hands.json; everything else stays in data/seq/<SEQ>.json. Both files are written from the same pass, on the same frame grid, and each carries its own license string — see Two files per recording for why.
  4. The MPS streams are mapped through the timecode. SLAM and eye gaze are stamped in Aria device time while the annotations are stamped in the recording's timecode, so timecode_devicetime_mapping.csv converts before sampling. The payload keeps the first timecode, — ns. The closed-loop trajectory arrives at — (— samples here) and is sampled down to one pose per frame; its per-sample quality score is carried across as-is, including where the release leaves it empty.
  5. Semidense points are filtered, then evenly subsampled. Points whose dist_std — the MPS per-point distance standard deviation, in metres — is above — are dropped, and the rest are thinned by a fixed stride so the shipped cloud stays around 60k points and still covers the whole room: —.
  6. Video is re-rendered from the VRS. The RGB stream is rotated 90° clockwise to upright, scaled from — to —, and encoded as H.264 at CRF —, — fps, so mp4 frame i is payload row i. The SLAM cameras get — stills each instead of video, evenly spaced through the recording, plus one poster frame for the player.
  7. Object models are compacted. The 33 released meshes have their textures resampled to at most — px and their geometry decimated to at most 40k faces, then are written as glb: — triangles across the library and — on disk. —

Conventions a reader needs

quaternions
w, x, y, z — the release's order, kept everywhere on this site, in the payload and in assets/site.js.
poses
A pose maps its own frame to world: an object pose takes a point of that object's model to world coordinates, the headset pose takes a point in the device frame to world. There is no inverse convention anywhere in the payload.
units
Metres, seconds, radians. t is seconds from the first RGB frame, not device time.
NaN
A float array carries NaN on every frame the release does not annotate — a hand out of view, an occluded object, a frame outside the annotated range. Gaps are never interpolated, and the charts on this site leave them open rather than bridging them.
mask 255
Masks are uint8: 1 true, 0 false, 255 not annotated. Treating 255 as true, or as a large number, is the easy mistake.
2D boxes
box_frame is —: boxes are stored in the upright display frame, already rotated to match the video and the stills, so a page scales by videoWidth / display_wh[stream][0] and nothing else. Frame sizes here: —.
streams
— — the stream ids as VRS names them, mapped to the names the payload uses.

Provenance and terms

HOT3D is a release by Meta Reality Labs — see the project page and the paper, arXiv:2411.19167, published at CVPR 2025. The data is used here under its license, which ships as license.txt inside every download; the version behind this site is v4.0.0, and every Aria row in data/index.json reports release version —.

Licence

That licence sets three regimes, and everything this site serves falls under one of them.

Material Licence Where it is here
Sequence data — the camera streams and every annotation except the hand annotations CC BY-SA 4.0 data/seq/, media/, data/index.json
Hand annotations — wrist poses, joint angles, confidences, 2D hand boxes, and the hand_visible and hand_pose_available masks CC BY-NC-SA 4.0 — non-commercial data/hands/, and the Hands page
3D object models CC BY-SA 4.0, with Meta's rider that the material may not be sold, nor incorporated into a product that is sold data/objects/

The split of the derived payload into data/seq/<SEQ>.json and data/hands/<SEQ>.hands.json exists to keep the first two regimes apart: a single file carrying both could not be licensed, because BY-SA does not permit the extra NonCommercial restriction being imposed on BY-SA material. Each file names its own terms in its license field. MANO parameters are not republished in either file: their use is gated by the SMPL-X/MANO licence in addition to HOT3D's, so only UmeTrack ships here.

ShareAlike also requires that modifications be indicated. What was changed — the re-encoded video, the resampling onto the RGB frame grid, the rotated boxes, the filtered points and the decimated models — is listed on this page and stated again in DATA_LICENSE.md, which is the licence notice for everything under data/ and media/. The site's own code is MIT and is not derived from the dataset.

This site is not a mirror of the release. It serves derived visualisations of — of the — Aria recordings: a re-encoded 704 px video, a few MB of resampled annotations per recording, a thinned point cloud, and decimated object models. Nothing here is a substitute for the release; to train or evaluate on HOT3D, download it from the project page.

Of the 198 Aria recordings, — ship hand and object ground truth; the rest hold their annotations back as the benchmark's test split, and appear on this site only as metadata. Where ground truth is present it comes from a motion-capture system, so the poses are independent of anything estimable from the images themselves — which is what makes the release usable as a reference and not only as training data.

Rebuilding this site

  1. Download. Take the eight data pieces per recording listed above, using the URL manifest from the project page.
  2. Build the index. Read every recording's metadata.json, its RGB frame count and its VRS size into data/index.json — one row per recording, both devices.
  3. Extract a payload per featured recording. Resample the ground truth, the masks and the MPS streams onto the RGB frame grid as described above, and write each array as base64 float32 (uint8 for masks) into two files: the hand annotations and their two masks into data/hands/<SEQ>.hands.json, everything else into data/seq/<SEQ>.json with a hands_file pointer and a license string in each.
  4. Render media. One 704 px mp4, one poster and twelve SLAM stills per featured recording, with a <SEQ>_media.json recording the encode settings.
  5. Compact the object library. Resample textures, decimate meshes, write data/objects/<uid>.glb and the index data/objects.json with before and after counts.
  6. Serve the repo root. There is no build step: each page is one HTML file that loads assets/site.css and assets/site.js and fetches the JSON it needs.
